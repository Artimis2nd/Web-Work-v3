- **Date:** 2026-11-06
- **Status:** Draft / Under Review
- **Author:** Antigravity & Artimis2nd
- **Project:** Web-Work v3 (Wage Management System)

## 1. Intent and The Why (ที่มาและความตั้งใจ)

### ปัญหาเดิมที่พบ
ในระบบเดิม (Web-Work v2 - v3.0) การบันทึกใบงานประจำวัน (`daily_logs`) มุ่งเน้นไปที่การคิดคำนวณค่าแรงของคนงานรายบุคคลตามจำนวนชั่วโมงและไซต์งาน แต่มีปัญหาสำคัญในการบริหารงานหน้างานจริงคือ:
1. **ขาดการบันทึกการสั่งงานที่เป็นรูปธรรม:** เมื่อหัวหน้างาน/ผู้จัดการสั่งงานลูกน้องไป มักไม่มีประวัติบันทึกว่าสั่งใคร, สั่งวันไหน, กำหนดส่งเมื่อใด, งานทำที่จุดไหนอย่างละเอียด
2. **ไม่เห็นความคืบหน้าและประวัติการแก้ปัญหา:** ไม่รู้ว่างานคืบหน้าถึงกี่เปอร์เซ็นต์ ติดปัญหาอะไร แก้ไขอย่างไร และสรุปผลการทำงานจริงเป็นอย่างไร
3. **ไม่สามารถคำนวณต้นทุนต่อชิ้นงานได้ทันที:** ข้อมูลค่าแรงรายวันไม่ได้ถูกผูกเข้ากับ "ชิ้นงานหรือคำสั่งงาน" โดยตรง ทำให้เวลาปิดงานไม่สามารถสรุปได้ว่างานชิ้นนี้ทำไปกี่วัน ใช้แรงงานไปกี่คน/กี่แรง และคิดเป็นต้นทุนค่าแรงรวมทั้งหมดเท่าไหร่

### ความตั้งใจใหม่
เพิ่มระบบ **"รายการสั่งงาน/มอบหมายงาน (Job Orders / Tasks)"** ที่ทำงานผสานร่วมกับระบบบันทึกค่าแรงรายวันเดิมอย่างไร้รอยต่อ เพื่อให้สามารถ:
* สั่งงานและติดตามสถานะงานได้จากที่เดียว
* ให้ลูกน้องหรือหัวหน้างานเลือกงานที่ได้รับมอบหมายเมื่อกรอกใบงานรายวัน และอัปเดต % ความคืบหน้า/ปัญหาหน้างานได้ในขั้นตอนเดียว
* รวมยอดสรุปเป็นรายงานต้นทุนตามชิ้นงาน (Task Cost & Effort Report) แสดงยอดวันทำงาน, แรงงานรวม, ค่าแรงจริง และยอดคิดเงินลูกค้าได้อย่างแม่นยำ

## 2. Goals, Non-Goals, and Anti-Goals

### Goals (เป้าหมายหลัก)
1. **หน้าจัดการงาน (`tasks.html`):** สร้างคำสั่งงานใหม่, กำหนดผู้รับผิดชอบ, ไซต์งาน, วันที่สั่ง, กำหนดแล้วเสร็จ, รายละเอียดงาน, และบันทึกปัญหา/แนวทางแก้ไข/สรุปผล
2. **ระบบสถานะงาน:** รองรับสถานะงาน `Pending` (รอดำเนินการ), `In Progress` (กำลังทำ), `Blocked` (ติดปัญหา), `Completed` (เสร็จสมบูรณ์) พร้อมเปอร์เซ็นต์ความคืบหน้า 0–100%
3. **การเชื่อมโยงกับใบงานรายวัน (`daily-log.html`):**
   * รองรับการทำงาน **หลายงาน/หลายไซต์ใน 1 วัน**: เช่น เช้าทำงาน A (บันทึกใบงาน A) และบ่ายทำงาน B หรือไซต์ B (บันทึกใบงาน B แยกกัน) โดยแต่ละใบงานจะผูกกับ Task ของตัวเองอย่างเป็นอิสระ
   * มีตัวเลือกให้เลือก "งานที่ได้รับมอบหมาย" ที่ยังไม่เสร็จ (กรองตามไซต์งาน หรือแสดงทุกงานที่กำลังทำ)
   * เมื่อเลือกงาน ระบบจะเติมชื่อไซต์งานและรายละเอียดให้อัตโนมัติ
   * สามารถอัปเดตความคืบหน้า (%) และบันทึกปัญหา/วิธีแก้ไขของงานนั้นๆ ลงในใบงาน ซึ่งจะไปปรับปรุงตารางงานหลักโดยอัตโนมัติ
   * การคำนวณชั่วโมงทำงาน (เช่น เช้า 4 ชม. + บ่าย 4 ชม.) จะกระจายต้นทุนค่าแรงไปยังแต่ละ Task ตามจริงอย่างถูกต้อง 100%
4. **รายงานต้นทุนตามชิ้นงาน (`task-cost-report.html` หรือแท็บรายงานสรุป):**
   * ดึงข้อมูลงานที่สั่ง + ข้อมูลบันทึกค่าแรงประจำวันที่ผูกกับงานนั้น
   * แสดงสรุป: ความคืบหน้า, จำนวนวันทำงานจริง, จำนวนแรงงานรวม (Man-Days / Total Hours), ยอดรวมค่าแรงจริง (Raw Wage), และยอดรวมคิดลูกค้า (Markup Wage)
5. **รองรับ Dual-Mode:** ทำงานได้ทั้งโหมด **Supabase Cloud (PostgreSQL)** และ **Local Storage Fallback** เหมือนกับระบบหลักของ Web-Work v3

### Non-Goals (สิ่งที่ไม่ทำในรอบนี้)
* ระบบแจ้งเตือนผ่าน LINE / SMS / Push Notification อัตโนมัติ (จะเน้นเป็น Web Interface ก่อน)
* ระบบ Gantt Chart ที่ซับซ้อนเกินไป (เน้นเป็น Task Cards / List และ Status Filter ที่ใช้งานง่ายบนมือถือและคอมพิวเตอร์)
* การกำหนดสิทธิ์แบบ Multi-Tenant / Role-based Authentication แบบละเอียด (ยังคงใช้โมเดลเดิมของโปรเจกต์คือ Anon Key + Master PIN ป้องกันหน้าสำคัญ)

### Anti-Goals (สิ่งที่ไม่ควรเกิดขึ้น)
* อย่าทำให้การกรอกใบงานประจำวันเดิม (`daily-log.html`) ช้าลงหรือยุ่งยากขึ้น (หากเป็นงานจรหรืองานทั่วไปที่ไม่ได้สร้าง Task ไว้ล่วงหน้า ต้องยังคงสามารถพิมพ์รายละเอียดงานเองได้ตามปกติโดยไม่ต้องเลือก Task)
* อย่าทำให้เกิด Breaking Change กับข้อมูลใบงานเดิมในฐานข้อมูล (ต้องรองรับข้อมูลเก่าที่ `task_id` เป็น null)

## 3. Constraints (ข้อจำกัดทางเทคนิคและสถาปัตยกรรม)

1. **สถาปัตยกรรม Client-Side (Vanilla JS, HTML5, CSS3):** ไม่ใช้ Framework ที่ต้อง Compile (เช่น React หรือ Vue) เพื่อให้คงคอนเซปต์ของ Web-Work v3 ที่เปิดไฟล์รันได้ทันที
2. **ธีม UI:** ใช้โทนสีและสไตล์ "สมุดบันทึกงานไซต์ก่อสร้าง" (Blueprint & Ledger) ตาม `assets/css/style.css`
3. **Supabase & LocalStorage Compatibility:**
   * สคริปต์ SQL ต้องเข้ากันได้กับ Postgres บน Supabase พร้อม Row Level Security (RLS)
   * ฟังก์ชันใน `assets/js/api.js` ต้องรองรับทั้ง Supabase REST API และการจำลองใน `localStorage` กรณีออฟไลน์/ยังไม่ต่อคลาวด์

## 4. Approaches Considered (แนวทางที่พิจารณา)

### แนวทางที่ 1: ระบบคำสั่งงานเชื่อมโยงใบงานอัตโนมัติ (Integrated Job Orders & Cost Tracking) — *[เลือกแนวทางนี้]*
* **ลักษณะ:** สร้างตาราง `tasks` และเพิ่มฟิลด์ `task_id` ในตาราง `daily_logs`
* **ข้อดี:**
  * ข้อมูลมีความสัมพันธ์กันแบบ Relational ชัดเจน
  * การคำนวณต้นทุนทำได้แม่นยำ 100% โดยการ Query `WHERE task_id = :id`
  * การใช้งานหน้างานราบรื่น ลูกน้องเลือกงานจากดรอปดาวน์ช่วยลดการพิมพ์ผิดหรือสะกดชื่อไซต์งานไม่ตรงกัน
* **ข้อเสีย:** ต้องอัปเดตสคริปต์ `schema.sql` และปรับปรุงฟอร์มใน `daily-log.html`

### แนวทางที่ 2: ระบบสั่งงานแบบแยกส่วนโดยใช้ข้อความจับคู่ (Standalone Task Log with Text Matching)
* **ลักษณะ:** บันทึกงานแยกต่างหาก แล้วเวลาสรุปรายงานใช้ชื่อไซต์งานหรือคีย์เวิร์ดมาจับคู่กับใบงานประจำวัน
* **ข้อดี:** ไม่ต้องแตะต้องโครงสร้างตาราง `daily_logs`
* **ข้อเสีย:** ข้อมูลเสี่ยงต่อความคลาดเคลื่อนสูงมาก หากพิมพ์ชื่อไซต์หรือชื่องานต่างกันนิดเดียว (เช่น "บ้านคุณเอ" กับ "บ้านคุณ A") ข้อมูลต้นทุนจะไม่เชื่อมกัน ทำให้สรุปรายงานผิดพลาด

**เหตุผลที่เลือกแนวทางที่ 1:** มอบความถูกต้องแม่นยำของข้อมูลต้นทุน ซึ่งเป็นหัวใจสำคัญของผู้ใช้งานในการตรวจสอบกำไร-ขาดทุนของแต่ละงาน และยังช่วยลดความผิดพลาดในการกรอกข้อมูลของลูกน้อง

## 5. Technical Specifications & Architecture (ข้อกำหนดทางเทคนิค)

### 5.1 โครงสร้างฐานข้อมูล (Database Schema)

#### ตารางใหม่: `public.tasks`
```sql
CREATE TABLE IF NOT EXISTS public.tasks (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    task_code TEXT NOT NULL UNIQUE,          -- เช่น TSK-202611-001
    title TEXT NOT NULL,                     -- ชื่องาน / หัวข้องาน
    site TEXT NOT NULL DEFAULT '',           -- ไซต์งาน / สถานที่
    location_detail TEXT DEFAULT '',         -- ตำแหน่งจุดทำงานโดยละเอียด เช่น ชั้น 2 ห้องนอนใหญ่
    assigned_to TEXT DEFAULT '',             -- ผู้รับผิดชอบหลัก / หัวหน้าชุดช่าง
    ordered_by TEXT DEFAULT '',              -- ผู้สั่งงาน
    order_date DATE NOT NULL DEFAULT CURRENT_DATE, -- วันที่สั่งงาน
    due_date DATE,                           -- กำหนดแล้วเสร็จ
    status TEXT NOT NULL DEFAULT 'Pending' 
        CHECK (status IN ('Pending', 'In Progress', 'Blocked', 'Completed')),
    progress_percent INT NOT NULL DEFAULT 0 CHECK (progress_percent BETWEEN 0 AND 100),
    description TEXT DEFAULT '',             -- รายละเอียดงานที่สั่ง
    issues TEXT DEFAULT '',                  -- ปัญหาและอุปสรรคปัจจุบัน
    resolution TEXT DEFAULT '',              -- แนวทางการแก้ไขปัญหาปัจจุบัน
    completion_summary TEXT DEFAULT '',      -- สรุปผลการดำเนินงานเมื่อปิดงานโดยหัวหน้างาน
    
    -- ประวัติความคืบหน้าและการแก้ไขปัญหาแบบ Timeline (ไม่เขียนทับ)
    -- โครงสร้าง JSON: [{"date": "2026-11-06", "percent": 30, "issues": "...", "resolution": "...", "by": "..."}]
    progress_history JSONB NOT NULL DEFAULT '[]'::jsonb,

    -- ยอดสะสมจากการเบิกงวดในรอบก่อนหน้า (Accumulated Snapshot) ป้องกันข้อมูลหายเมื่อกดล้างบันทึกรอบค่าแรง
    accumulated_cost NUMERIC(12, 2) NOT NULL DEFAULT 0,
    accumulated_markup_cost NUMERIC(12, 2) NOT NULL DEFAULT 0,
    accumulated_hours NUMERIC(8, 2) NOT NULL DEFAULT 0,
    accumulated_man_days NUMERIC(8, 2) NOT NULL DEFAULT 0,
    accumulated_days INT NOT NULL DEFAULT 0,

    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Index สำหรับค้นหาตามสถานะ ไซต์งาน และรหัสงาน
CREATE INDEX IF NOT EXISTS idx_tasks_status ON public.tasks (status);
CREATE INDEX IF NOT EXISTS idx_tasks_site ON public.tasks (site);
CREATE INDEX IF NOT EXISTS idx_tasks_task_code ON public.tasks (task_code);
```

#### ปรับปรุงตารางเดิม: `public.daily_logs`
* เพิ่มคอลัมน์ `task_id` (BIGINT, NULL ได้ เพื่อรองรับงานทั่วไปที่ไม่ผ่านคำสั่งงาน)
```sql
ALTER TABLE public.daily_logs ADD COLUMN IF NOT EXISTS task_id BIGINT REFERENCES public.tasks(id) ON DELETE SET NULL;
CREATE INDEX IF NOT EXISTS idx_daily_logs_task_id ON public.daily_logs (task_id);
```

### 5.2 กฎการคำนวณและวงจรชีวิตข้อมูล (Business Logic & Lifecycles)
1. **การเบิกงวดและล้างบันทึกรายวัน (Wage Cycle Retention):**
   * เมื่อผู้ใช้สั่ง "เบิกงวด / ล้างบันทึกใบงาน" ใน `index.html` (Dashboard):
   * ระบบจะทำการคำนวณค่าแรงและจำนวนแรงงานปัจจุบันของแต่ละ Task ที่ยังไม่เสร็จ (`status != 'Completed'`) แล้วบวกทบเข้าสู่ฟิลด์ `accumulated_*` ในตาราง `tasks`
   * หลังจากนั้นจึงทำการล้าง `daily_logs` ทำให้รอบบันทึกรายวันว่างเพื่อเริ่มรอบใหม่ แต่งานแต่ละชิ้นจะยังมียอดสะสมประวัติเงินและแรงงานครบถ้วน 100%
2. **ประวัติความคืบหน้า (Progress History Timeline):**
   * เมื่อมีการบันทึกใบงานประจำวันที่ผูกกับ Task หรือมีการอัปเดตผ่านหน้า `tasks.html` ระบบจะเพิ่ม Object ใหม่ลงใน `progress_history` เสมอ
   * แสดงผลเป็น Timeline ในหน้าต่างดูรายละเอียดงาน ย้อนดูได้ทุกวันว่าวันไหนติดปัญหาอะไร ใครแก้อย่างไร
3. **วงจรชีวิตสถานะงาน (Task Status Transitions):**
   * `Pending` -> `In Progress`: เปลี่ยนอัตโนมัติเมื่อมีบันทึกใบงานประจำวันฉบับแรกผูกกับ Task นั้น
   * `In Progress` -> 100%: เมื่อคนงานกรอกความคืบหน้า 100% ในใบงานรายวัน Task จะยังคงอยู่ เพื่อรอให้หัวหน้างานเข้ามาตรวจสอบงาน
   * `Completed`: หัวหน้างานตรวจรับงานใน `tasks.html`, บันทึก `completion_summary`, และกดยืนยันปิดงาน
4. **การคำนวณแรงงาน (Man-Days Calculation):**
   * คนงานรายชั่วโมง: `hours / 8`
   * คนงานเหมาจ่าย (`wage_type = 'fixed'`): นับเป็น `1.0 Man-Day` ต่องานในวันนั้น
   * รวมต้นทุนทั้งสิ้น = ยอดสะสมในอดีต (`accumulated_*`) + ยอดในรอบปัจจุบันจาก `daily_logs`

### 5.2 ฟังก์ชัน API ใน `assets/js/api.js`
1. `getTasks(filter)`: ดึงรายการงาน รองรับตัวกรองสถานะ (`Pending`, `In Progress`, `Completed`, etc.) และไซต์งาน
2. `getTaskById(id)`: ดึงข้อมูลงานเดี่ยวพร้อมรายละเอียด
3. `createTask(taskData)`: สร้างคำสั่งงานใหม่ พร้อมสร้าง `task_code` อัตโนมัติ (เช่น `TSK-YYYYMM-XXX`)
4. `updateTask(id, taskData)`: แก้ไขข้อมูลงาน, สถานะ, % ความคืบหน้า, ปัญหา/วิธีแก้ไข
5. `deleteTask(id)`: ลบงาน (เฉพาะผู้มีสิทธิ์ / ยืนยัน PIN)
6. `getTaskCostSummary(taskId)`: รวมข้อมูลจาก `daily_logs` ที่มี `task_id = taskId`:
   * รายการวันที่ที่มีการลงงาน (`work_date`)
   * รายชื่อคนงานที่ร่วมทำ (`worker_name`)
   * รวมชั่วโมงทำงาน (`hours`), ชั่วโมง OT (`ot_hours`), จำนวนเหมาจ่าย
   * คำนวณจำนวน Man-Days (ชั่วโมงรวม / 8)
   * คำนวณยอดรวมค่าแรงจริง (`raw_wage`) และยอดรวมคิดลูกค้า (`total_with_markup`)

### 5.3 ส่วนติดต่อผู้ใช้ (UI / UX Flow)

#### 1. หน้ากระดานงาน (`tasks.html`)
* **ส่วนบน:** สถิติตัวเลขสรุป (KPIs): งานทั้งหมด, กำลังทำ, ติดปัญหา, เสร็จสมบูรณ์
* **แถบตัวกรอง & ค้นหา:** กรองตามสถานะ, ไซต์งาน, หรือค้นหาตามชื่องาน/ผู้รับผิดชอบ
* **ปุ่ม "➕ สั่งงานใหม่":** เปิด Modal บันทึกข้อมูลคำสั่งงาน
* **รายการงาน (Task Cards / Table):**
  * แสดง Progress Bar 0–100%
  * Badge แสดงสถานะ (`Pending`, `In Progress`, `Blocked`, `Completed`)
  * ปุ่ม "ดูความคืบหน้า & บันทึกปัญหา", ปุ่ม "ดูสรุปต้นทุนค่าแรง", ปุ่ม "แก้ไข"
* **Sidebar Menu:** เพิ่มเมนู **"📋 สั่งงานและติดตามงาน"** ใน `utils.js`

#### 2. หน้าบันทึกใบงานประจำวัน (`daily-log.html`)
* ในส่วนหัวของฟอร์ม (ถัดจากวันที่):
  * เพิ่ม Dropdown: **"งานที่ได้รับมอบหมาย (ถ้ามี)"**
  * เมื่อผู้ใช้เลือกงาน: ระบบจะดึงชื่อไซต์งานและรายละเอียดงานมาใส่ให้อัตโนมัติ
  * เพิ่มช่องย่อย: **"ความคืบหน้าของงาน (%)"** และ **"ปัญหาที่พบ/วิธีแก้ไขวันนี้"** (บันทึกอัปเดตกลับไปยัง Task หลักเมื่อกดบันทึกใบงาน)
  * หากไม่เลือกงาน: ผู้ใช้สามารถกรอกไซต์และรายละเอียดงานอิสระได้เหมือนเดิม 100%

#### 3. หน้ารายงานสรุปต้นทุนตามชิ้นงาน (`task-cost-report.html` หรือแท็บในหน้ารายงาน)
* แสดงรายละเอียดหัวงาน: รหัสงาน, ชื่องาน, ไซต์, ผู้สั่งงาน, ระยะเวลาที่ทำ (เริ่มวันไหน ถึงวันไหน)
* สถานะปัจจุบันและสรุปวิธีแก้ไขปัญหา
* ตารางแจกแจงค่าแรง:
  * แสดงรายชื่อคนงานแต่ละคนที่เข้ามาทำในงานนี้ พร้อมจำนวนวัน/ชั่วโมงที่ทำ และค่าแรงรวม
* การ์ดยอดรวมสุทธิ:
  * จำนวนวันทำงานจริง (Actual Days)
  * จำนวนแรงงานรวม (Total Man-Days)
  * ต้นทุนค่าแรงจริง (Total Cost Wage)
  * ยอดรวมค่าแรงคิดลูกค้า (Total Billable Wage with Markup +20%)
